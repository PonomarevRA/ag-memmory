# План развития областей памяти, просмотра данных и прозрачности использования

## Цель

Сделать локальную память понятной и управляемой:

1. одинаковые теги из разных предметных областей не смешиваются;
2. записи можно просматривать в табличном представлении, близком к БД;
3. видно фактическое обращение агентов к памяти за последние сутки;
4. в UI вновь есть понятные разделы «О проекте» и «Подключение агента».

## Подтверждённая исходная ситуация

- `MemoryScope` уже состоит из tenant, project, workspace, chat и run; сопоставление строго точное, без иерархии или префиксного поиска. Поэтому записи из разных точных scope изолированы, но отдельной предметной области внутри scope нет.
  Источник: `src/AgMemory.Contracts/Domain.cs`.
- MCP получает scope только из окружения процесса. Агент не может подставить scope в вызове инструмента.
  Источник: `src/AgMemory.McpServer/LocalAgMemoryMcpRuntime.cs`, `src/AgMemory.McpServer/AgMemoryTools.cs`.
- Wiki-каталог, дерево и теги строятся в одном server-configured exact scope. Смешение тегов между разными областями не доказано как ошибка хранилища: оно возможно при слишком широком scope или отсутствии отдельной предметной области внутри него.
  Источник: `src/AgMemory.Contracts/Queries/MemoryReader.cs`, `src/AgMemory.Web/Features/MemoryReader/MemoryReaderEndpoint.cs`.
- У записи есть оценка числа токенов и provenance, но обращение `memory_recall` и построение контекста не сохраняют аудит. Исторические обращения и выданные токены за сутки сейчас восстановить нельзя.
  Источник: `src/AgMemory.Contracts/Domain.cs`, `src/AgMemory.McpServer/LocalAgMemoryMcpRuntime.cs`, `src/AgMemory.Web/Features/Chat/LocalChatMemoryFeature.cs`.
- `/about` и `/connect` существуют, но сейчас содержат лишь краткие тексты; фактическая инструкция подключения находится в `README.md`.

## Решения, которые нужно утвердить до реализации

1. **Граница области.** Сначала составить операционную карту: какая предметная область соответствует каждому из пяти current scope fields, каков разрешённый набор значений и какие процессы используют один store. Если карта достаточна, не менять контракт. Только при доказанной недостаточности утвердить отдельный `KnowledgeSpaceId`; это breaking-миграция, а не взаимозаменяемое поле.
2. **Табличный просмотр.** Утвердить детерминированную field policy: исходный текст только по явному локальному разрешению, provenance только как allowlisted client label, durable ID и полный raw scope никогда не передаются. По умолчанию выдавать безопасный row key, preview и разрешённые метаданные.
3. **Оценка экономии.** До утверждения baseline, формулы, округления и версии методики показывать только измеренную оценку выданных токенов. «Потенциально сэкономлено» — `не рассчитано`, а не предположение.
4. **Срок хранения аудита.** Окно UI — 24 часа; рекомендуемое хранение событий — 30 дней локально, без внешней отправки.

## Рабочие пакеты

Детализация по приоритетам и отдельным задачам находится в [improvement-plan/README.md](improvement-plan/README.md).

### A. Decision gate для областей памяти

**Владелец:** архитектор + Core-разработчик.
**Зависимости:** нет.

- Описать mapping предметных областей на tenant/project/workspace/chat/run, владельца словаря и максимальную cardinality каждого поля.
- Зафиксировать, какие MCP/Web процессы должны запускаться с разными конфигурируемыми scope, когда им нужен общий store, но разные области.
- Принять решение: текущего mapping достаточно или нужен `KnowledgeSpaceId`.
- Только после решения о новом поле добавить его в контракты, exact comparison, авторизацию, ключи хранения, каталог, граф и настройки Web/MCP. Значение остаётся конфигурацией процесса, не параметром MCP-инструмента.
- Для breaking-варианта подготовить явную `legacy`-область; не угадывать область по тексту и не объединять legacy с новой областью молча.

**Приёмка:** одинаковый тег в разных областях не попадает в один поиск, facet, дерево, граф или audit-view без явного выбора области.

### B. Теги, поиск и Wiki с учётом области

**Владелец:** Core + Storage + Web-разработчик.
**Зависимости:** A.

- Закрепить ключ фасетов как `(knowledge-space, normalized-tag)`, а не как один текстовый тег.
- В API каталога и тегов возвращать safe locator и label только активной области; continuation привязать к области, фильтру и поколению каталога.
- В UI показать выбранную область рядом с фильтрами, переключать только server-authorized области и очищать search/tag/continuation при её смене.
- Сохранить opaque-навигацию и текущие ограничения reader.

**Тесты:** одинаковые теги в двух областях; смена области при пагинации; подделанный continuation; поиск и дерево после смены области.

### C. Просмотр памяти как таблицы

**Владелец:** Web + Core/Storage-разработчик.
**Зависимости:** A.

- Добавить отдельный read-only раздел «Записи памяти», не превращая Wiki в административный экран.
- Серверная постраничная проекция exact scope: тип, статус, preview, теги, даты, importance, confidence, оценка токенов, expiry и разрешённая provenance-проекция.
- Фильтры: область, тип, lifecycle status, тег, полнотекстовый запрос, дата обновления; сортировка только по whitelist полей.
- Курсоры opaque; прямой доступ браузера к LanceDB запрещён.
- UI: таблица, детали строки справа, режим сокращённого/скрытого текста и явные empty/unavailable states.

**Тесты:** pagination/filter/sort, cross-scope denial, скрытие запрещённых полей, отсутствие полной выгрузки, keyboard flow.

### D. Журнал использования памяти

**Владелец:** Contracts/Core/Storage + MCP-разработчик.
**Зависимости:** A.

- Ввести append-only `MemoryUsageEvent`: время UTC, pseudonymous configured audit label, operation (`recall`, `remember`, `status`, `build-context`), область, outcome, число результатов, delivered token estimate, duration и privacy-safe query descriptor. `AGMEMORY_CLIENT_ID` — метка хоста-клиента, а не доверенный actor из browser-запроса.
- Для query утвердить один режим: ограниченный и отредактированный текст с TTL либо salted hash + длина.
- Для токенов зафиксировать estimator, правило округления и `estimationMethodVersion`; это оценка контекста, не provider billing.
- Не писать в audit секреты, содержимое возвращённых memories, chain-of-thought или durable IDs в browser-ответах.
- Событие успешной операции пишется после завершения этой операции; неуспех операции и неуспех audit фиксируются различимыми outcome. Работа инструмента не блокируется при недоступном audit: технический журнал отмечает degraded-state, но не подменяет факт записанным событием.

**Приёмка:** новый вызов каждого инструмента создаёт ровно одно корректно scoped событие; старые события неизменяемы; период до включения аудита не имитируется.

### E. Суточная статистика и оценка экономии

**Владелец:** Core/Storage + Web-разработчик.
**Зависимости:** D.

- Новый read-only API «последние 24 часа»: обращения по агентам и операциям, суммарные delivered token estimate, ошибки/нулевые результаты и временная шкала.
- В UI: время, агент, операция, query descriptor, токены, число результатов, состояние; данные постраничны.
- `potentialTokensSaved` появляется только вместе с версией формулы и наблюдаемым baseline. Предлагаемая формула: `max(0, baselinePromptTokens - deliveredMemoryTokens)`.
- Подписи: «выдано памятью», «оценка по формуле v1», «нет данных до даты включения журнала».

**Тесты:** граница 24 часов по UTC, агрегация агентов, нулевой baseline, redaction query, отсутствие старых событий.

### F. «О проекте» и «Подключение агента»

**Владелец:** Web-разработчик + technical writer.
**Зависимости:** нет для восстановления текущего подтверждённого текста; обновление описания domain зависит от A.

- Вернуть полноценный «О проекте»: назначение, локальное хранение, основные разделы UI, границы безопасности и ограничения продукта.
- «Подключение агента»: инструкции Codex/Cursor/Claude на базе README, объяснение storage path, actor, client id и scope/domain; правило общей и изолированной памяти. В UI использовать только плейсхолдеры, не реальные значения.
- Дать ручную инструкцию проверки `memory_status → memory_remember → memory_recall`; browser не вызывает MCP-инструменты напрямую. Отдельный loopback-only server-side diagnostic возможен только в отдельном согласованном пакете.
- Не выводить реальные пути, действующие scope или секреты в DOM.

**Тесты:** route/navigation, отсутствие secret-like values, соответствие инструкции поддерживаемым MCP-инструментам и environment variables.

### G. Интеграция, миграция и rollout

**Владелец:** release owner + QA + security reviewer.
**Зависимости:** A–F.

- Для breaking-варианта scope/domain: export/copy исходного LanceDB, freeze записи, transform всех scope-bearing records, reader catalog/routes/relations, затем validate и cutover marker. Исходная копия остаётся нетронутой для rollback; reader явно различает legacy и новую схему.
- Не начинать backfill до проверяемого backup/rollback и теста миграции на копии LanceDB.
- Feature flags: selector области, raw-record browser, audit writing, usage dashboard. Новые content-bearing/admin endpoints выключены вне Development/loopback.
- Прогнать существующие reader/MCP/graph/status регрессии вместе с новыми контрактными и e2e тестами.
- Rollout: 1) восстановить About/Connect и утвердить mapping scope, 2) аудит без dashboard, 3) 24 часа фактов, 4) dashboard и raw read-only view, 5) при утверждённой необходимости migration/selector для тестовой области, 6) расширение после проверки изоляции.

**Критерий завершения:** видимые цифры имеют источник и период; scope/knowledge-space не обходится URL, continuation или API; README и UI согласованы.

## Сквозные границы

- Сохраняются LanceDB, exact-scope authorization и три MCP-инструмента `memory_recall`, `memory_remember`, `memory_status`, пока отдельное решение не утвердит расширение.
- Browser/MCP не передаёт scope, actor, storage path или client identity как доверенный параметр.
- «Сэкономленные» токены не объявляются фактом без утверждённого baseline.
- Runtime AgMemory и файловая `docs/agent-memory/` остаются разными системами.
