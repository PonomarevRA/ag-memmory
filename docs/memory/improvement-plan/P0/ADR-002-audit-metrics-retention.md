# ADR-002. Локальный аудит использования памяти, метрики и хранение

**Статус:** принято
**Версия политики:** `usage-audit/v1`
**Владелец:** архитектор + privacy reviewer
**Реализуется в:** P1.5–P1.9

## Решение

После включения telemetry каждая попытка получить память или построить
контекст может создать одно локальное событие usage-аудита. Это журнал
наблюдаемости, а не журнал содержимого памяти, биллинг провайдера или источник
исторической статистики за прошлые периоды. В production и вне loopback/
Development доступ к журналу запрещён правилами P0.5.

По умолчанию запрос хранится как `queryDescriptor`: keyed salted hash от
нормализованного запроса и его длина в символах. Секрет HMAC локальный,
отдельный от пользовательских данных, не покидает машину и ротируется не реже
срока хранения; значение хеша нельзя использовать для восстановления текста.
Исходный запрос, raw scope, durable IDs, токены авторизации, evidence,
embeddings и пути хранилища в событие не попадают.

## Поля события `usage-audit/v1`

| Поле | Разрешено хранить | Назначение и ограничение |
| --- | --- | --- |
| `eventId`, `occurredAt`, `schemaVersion` | Да | Случайный идентификатор, UTC-время, `usage-audit/v1`; не ID памяти. |
| `source` | Да | Allowlist: `mcp` или `local-chat`. |
| `operation` | Да | Allowlist операции (`recall`, `context-build`); без аргументов вызова. |
| `clientLabel` | Да | Только короткий label из allowlist серверной конфигурации; не actor ID, user, host или path. |
| `areaId` | Да, опционально | Только безопасный opaque slug; контракт P1.5 проверяет лишь его структуру. Принадлежность server-configured каталогу P1.1 проверяют P1.6/P1.7 до построения и сериализации события. Метка неавторитетна для доступа и не содержит raw scope. |
| `outcome`, `failureClass` | Да | `succeeded`, `failed` или `degraded`; класс без текста исключения. |
| `queryHash`, `queryLengthChars` | Да | Только HMAC-hash и длина; исходный запрос запрещён. |
| `resultCount` | Да | Количество отобранных записей; не их идентификаторы. |
| `selectedContextChars` | Да | Размер выбранного текста до рендеринга промпта. |
| `deliveredTokensEstimate`, `estimationMethodVersion` | Да | Оценка по правилам ниже; не provider usage. |
| scope, actor, memory IDs, record text | Нет | Нельзя писать в audit event или отдавать через его API. |

`source`, `operation`, `outcome`, `failureClass` и `clientLabel` — закрытые
allowlist-значения. `clientLabel` разрешается только после серверной
валидации: входные actor ID, user, host, path и свободный текст не
сериализуются. `areaId` может отсутствовать. `UsageAuditEvent` P1.5 не
зависит от Web-каталога P1.1 и принимает только структурно корректный opaque
slug; он не проверяет членство в области. MCP- и local-chat emitter’ы P1.6 и
P1.7 обязаны до построения события сверить slug с server-configured каталогом
P1.1: неизвестный slug отклоняется или заменяется отсутствующим `areaId`, но
никогда не сериализуется как `unknown`. Метка остаётся только наблюдаемостью,
не selector и не источник authority. Ни одно из этих полей не разрешает запись
raw scope. Текст ошибки и stack trace не сохраняются.

## Семантика результата и метрик

`succeeded` означает: операция памяти завершилась и результат был передан
вызывающему слою. `failed` означает: операция не дала результата; сохраняется
только безопасный `failureClass` (`validation`, `authorization`, `storage`,
`timeout`, `unknown`). `degraded` означает: операция вернула разрешённый
упрощённый результат (например, пустой контекст при недоступном необязательном
источнике); причина также задаётся только перечислением.

Для успешного `context-build` вычисляется `deliveredTokensEstimate`:
`min(800, ceil(selectedContextChars / 4))`. В `v1` это оценка выбранного
контекста: она не включает рендеринг, системный и пользовательский prompt,
tool calls, ответ модели и токены провайдера. Для `recall`, `failed` и
`degraded` без переданного контекста значение равно `0`. Отображение всегда
подписывает его как «оценка токенов контекста» и показывает
`estimationMethodVersion = context-chars-div4-cap800/v1`.

`potentialTokensSaved` в `v1` отсутствует: поле и агрегат возвращаются как
`null`/«не рассчитано». Формула, baseline, источник контрольного измерения и
период сравнения требуют отдельного утверждения до появления показателя в API
или UI. Нельзя подменять его разностью с provider billing.

## Хранение, очистка и отказоустойчивость

События хранятся только локально 30 дней от `occurredAt` (UTC). Планировщик
очистки выполняется не реже одного раза в сутки, удаляет записи строго старше
30 дней и не отправляет их наружу. Окно dashboard «последние 24 часа» — это
фильтр по сохранённым событиям, а не обещание восстановления истории до
включения telemetry.

Сбой записи audit event не блокирует основную операцию памяти: она возвращает
свой честный результат, а вызов считается `audit-unavailable` для health
наблюдения. Нельзя ретроспективно создавать успешное usage-событие из логов
или повторного выполнения операции. При сбое очистки данные не удаляются
раньше срока; health-сигнал `usage-audit-cleanup-failed` содержит только время,
счётчик и безопасный класс ошибки. Успешная очистка фиксирует только время
последнего запуска и число удалённых записей.

## Правила приёмки P1

- Для каждого разрешённого источника и исхода записывается не более одного
  события `usage-audit/v1`; до включения telemetry событий нет.
- Тест контракта P1.5 доказывает отсутствие raw query, scope, actor, memory
  ID, текста записи, exception text, embedding и storage path; для `areaId` он
  проверяет только optional структурно корректный opaque slug. Тесты
  emitter’ов P1.6/P1.7 отдельно доказывают server-side membership в P1.1 и
  отсутствие/отклонение неизвестной области до сериализации.
- Тест hash-политики доказывает наличие длины и невозможность равенства поля
  исходному запросу; тесты не зависят от постоянного значения секрета.
- Для `801 * 4` символов оценка равна `800`; для 1–4 символов — `1`; тесты
  подтверждают версию метода и исключение prompt/output.
- Тесты исходов покрывают `succeeded`, `failed`, `degraded` и отказ самого
  audit writer: последний не меняет результат операции памяти.
- Детерминированный тест cleanup удаляет запись старше 30 дней, сохраняет
  более новую и публикует безопасный health-сигнал при ошибке очистки.
- API и UI показывают `potentialTokensSaved` только после отдельного
  утверждённого ADR с формулой и baseline; до этого показывают «не рассчитано».
