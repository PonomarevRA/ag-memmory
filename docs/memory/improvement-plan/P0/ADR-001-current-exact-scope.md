# ADR-001. Текущий exact scope как граница памяти

**Статус:** принято для P1; пересмотр по триггеру ниже
**Дата:** 2026-08-22
**Владелец решения:** владелец продукта памяти; согласуют владелец локальной инфраструктуры и security-владелец

## Контекст и подтверждённые факты

`MemoryScope` содержит ровно пять измерений: обязательный `tenant` и необязательные `project`, `workspace`, `chat`, `run`. `ScopeSelector.Matches` сравнивает каждое из них на равенство, включая отсутствие значения; иерархии, префиксного поиска и поля предметной области в контракте нет.

MCP получает storage path, actor и все пять значений только из переменных окружения процесса. Локальные Web-функции (reader, graph и chat) получают один server-configured storage path, actor и те же пять значений. Поэтому разные конфигурации процесса могут изолировать память, а совпадающие storage path и все пять значений намеренно дают общий store. Конкретная production-карта развёртываний, источники идентификаторов и владельцы их словарей в репозитории не определены.

## Операционная карта и требуемое согласование

| Измерение | Техническая роль сейчас | Допустимая cardinality | Владелец словаря / обязательное решение |
| --- | --- | --- | --- |
| `tenant` | обязательная верхняя exact-граница | один непустой идентификатор на scope | Владелец локальной инфраструктуры должен утвердить источник и жизненный цикл. |
| `project` | необязательная граница проекта | 0 или 1 значение на scope | Владелец продукта памяти утверждает, когда проекты разделяются. |
| `workspace` | необязательная граница рабочего пространства | 0 или 1 значение на scope | Владелец интеграции клиентов утверждает соответствие рабочему пространству клиента. |
| `chat` | необязательная граница беседы | 0 или 1 значение на scope | Владелец UI/клиента утверждает источник и срок жизни. |
| `run` | необязательная граница запуска | 0 или 1 значение на scope | Владелец оркестрации утверждает источник и срок жизни. |

Предметная область не сопоставлена ни с одним полем автоматически. До письменного утверждения эта таблица — governance-шаблон, а не описание действующего deployment. Утверждение должно назвать для каждого запускаемого процесса: выбранные пять значений, источник каждого значения, владельца словаря, storage path и правило «общий либо изолированный store».

| Процесс | Store и scope | Решение для общей памяти | Решение для изоляции |
| --- | --- | --- | --- |
| MCP: Codex / Cursor / Claude | фиксируются окружением процесса | одинаковые storage path и все пять exact-значений | отличается storage path или хотя бы одно из пяти значений |
| Web: reader / graph / local chat | фиксируются server-side host configuration | один storage path и одинаковый exact scope | отдельная host configuration с отличающимся store или exact scope |

## Решение

Для P1 сохраняем существующий `MemoryScope` и exact authorization. `KnowledgeSpaceId` не добавляется: нет подтверждённой коллизии, в которой две предметные области вынужденно используют одинаковые storage path и все пять значений, но должны быть изолированы. Это решение не утверждает новую схему, API или миграцию.

Текущая модель способна изолировать процессы при различной конфигурации exact scope. Она **не способна** разделить две предметные области, если они совместно используют один store и совпадают по всем пяти полям: их разделение невозможно выразить в текущем контракте.

## Триггер пересмотра

Владелец продукта памяти открывает P2 только после одобренного evidence-пакета: два разрешённых процесса/области, их одинаковые storage path и пять значений, требование раздельных результатов и невозможность изменить утверждённую карту значений без потери нужного общего контекста. Пакет согласуют владелец локальной инфраструктуры и security-владелец. После этого отдельный ADR определяет `KnowledgeSpaceId`, авторизацию, миграцию и rollback; данный ADR сам по себе не даёт такого разрешения.

## Последствия и проверка

- P1 реализует area-catalog только как серверную проекцию утверждённой exact-scope карты; ни browser, ни MCP tool не принимают raw scope как доверенный вход.
- До согласования карты допускаются только текущие локальные конфигурации из README; нельзя объявлять их моделью production-tenant или предметных областей.
- При изменении deployment-карты повторно проверить cross-scope denial для MCP, reader, graph и local chat.
